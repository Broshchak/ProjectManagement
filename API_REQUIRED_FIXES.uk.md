## Покупці

- GET /api/customers — повний список, зокрема покупці без замовлень.
- GET /api/customers/{id} — деталі покупця.
- POST /api/customers — створення.
- PUT /api/customers/{id} — зміна імені, телефону, email та адреси.
- Запит: fullName, phone, email, address. Повертається також id.
- При створенні замовлення customerId перевіряється на сервері.
- WPF завантажує довідник з API; додавання й редагування доступні у вікні вибору покупця. Створити перше замовлення можна й за порожнього початкового списку покупців.

## Користувачі

- GET /api/users та GET /api/users/{id} — дані без паролів і хешів.
- POST /api/users — створення з початковим password.
- PUT /api/users/{id} — зміна login, fullName, role, isActive, telegramAllowed, telegramUserId.
- PUT /api/users/{id}/password — окрема зміна пароля, тіло {"password":"..."}, відповідь 204.
- Перевіряються роль, унікальність логіна/Telegram ID і обов’язковий Telegram ID при дозволеному доступі. Нові логіни зберігаються в нижньому регістрі. Паролі хешуються існуючим PBKDF2-сервісом.
- WPF показує реальних користувачів; Admin може редагувати, Director — переглядати. Пароль вводиться в PasswordBox та змінюється окремою кнопкою. Після редагування власного облікового запису клієнт просить увійти повторно.
- Серверні політики доступу залишаються відкладеним пунктом 3; обмеження WPF не замінюють їх.

## Замовлення

GET /api/orders/{id} тепер повертає поле version. Це SHA-256 від поточного стану заголовка й рядків, без змін схеми бази.

PUT /api/orders/{id} приймає повний редагований склад і коментар:

```json
{
  "expectedVersion": "значення version із GET /api/orders/{id}",
  "comment": "Новий коментар",
  "items": [
    { "id": 10, "productId": 1, "quantity": 3 },
    { "id": 0, "productId": 2, "quantity": 1 }
  ]
}
```

- Ненульовий id — існуючий рядок; id = 0 — доданий товар. Відсутні у списку товари видаляються.
- Операція виконується у транзакції Serializable з блокуванням рядка замовлення FOR UPDATE. Старі маршрути додавання, видалення та зміни статусу використовують те саме блокування.
- Невдала операція відкочує весь набір змін. Застаріла версія чи конкурентний запис повертають 409.
- Редагуються лише NewOrder/Registered. Перевіряються товари, активність, залишки, кількості й дублікати. Порожнє замовлення заборонено.
- Кількість існуючого товару змінюється зі збереженням його рядка та історичної unitPrice. Нові товари отримують поточну ціну.
- WPF надсилає одну операцію для кількості, складу й коментаря; DELETE + POST для заміни не використовується.
- Для старого сервера без version редагування залишається заблокованим. Для недоступного customers API залишається явний обмежений вибір із реальних замовлень. Підміни demo-даними немає.

## Перевірка

```powershell
dotnet build ProjectManagement.slnx --no-restore -v minimal
dotnet run --project WpfClient.Tests/WpfClient.Tests.csproj
./WebApi.Tests/Run-LocalTests.ps1 -PostgresBin 'C:/path/to/PostgreSQL/bin'
```

- 26 клієнтських перевірок: HTTP-помилки, сесія, запізнілі відповіді, довідники, користувачі та окрема зміна пароля, атомарний запит і 409, звіти/PDF, рендеринг WPF.
- 14 інтеграційних перевірок API на PostgreSQL: п’ять звітів, періоди й порожні результати, CRUD довідників, входи після зміни пароля/активності, історична ціна, відкат після помилки БД, конкурентні збереження, старі item-маршрути та заборона редагування після переходу статусу.
- Скрипт створює окремий локальний кластер на 127.0.0.1:55439 та зупиняє його після тестів. Бінарні файли PostgreSQL мають бути доступні локально. Тестова база створюється з випадковим ім’ям і видаляється після виконання; налаштування опублікованої бази не читаються.
- Міграція схеми для цих змін не потрібна. Наявні таблиці та тригери з SQL/01_create_schema.sql мають бути встановлені.
- Розгортання на опублікований сервер не виконувалося. Для використання нових можливостей із поточним BaseUrl потрібно розгорнути оновлений API разом із клієнтом.
