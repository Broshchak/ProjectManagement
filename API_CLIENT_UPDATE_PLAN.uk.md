Дата: 25.10.2026. Перевірено робочу копію на `e314364`, включно з поточними незакоміченими змінами WPF.

## Що додалося

За reflog останній pull перевів checkout із `22c3c1e` на `e314364` (merge PR #21, Reports). Сукупний diff цього оновлення: 13 файлів, 1036 доданих рядків. Частина серверного коду звітів уже була в попередньому локальному коміті `22c3c1e`.

У гілці Reports додалися:

- П’ять API-звітів: замовлення за період, замовлення за дату, продажі товарів, низькі залишки, текстовий звіт для керівника.
- Методи HTTP- і mock-клієнтів для цих звітів, моделі та завантаження у MainViewModel.
- Вкладки звітності та експорт вибраної вкладки в PDF через QuestPDF.
- Окремі файли DTO звітів, які конфліктують із попереднім загальним ReportDtos.cs.

Незакомічені зміни у MainWindow.xaml/.cs, LocalizationManager.cs, MainViewModel.cs, KanbanView.xaml та ReportsView.xaml розглянуто окремо від змін GitHub. Їх не змінено.

## Що реально перевірено

- `dotnet build ProjectManagement.slnx --no-restore -v minimal`: WpfClient зібрався; повна збірка завершилася 12 помилками CS0101/CS8863 через повторні визначення шести DTO звітів.
- Прочитано опубліковану схему: https://project-management3.runasp.net/openapi/v1.json.
- Виконано лише читання віддаленого API, без зміни даних і без входу під користувачем.
- GET /api/orders і GET /api/products повернули 200; GET /api/auth/me без токена повернув очікуваний 401.
- Усі п’ять GET /api/reports/* повернули 500. У відповідях orders, orders/today, products, low-stock підтверджено InvalidOperationException: EF Core не може перевести LINQ у SQL. Manager-summary залежить від orders.
- Вхід, операції запису та UI-сценарії наскрізно не перевірялися; їх сумісність оцінена за кодом і DTO.

## Наскільки клієнт відповідає API

У схемі 19 операцій. HTTP-клієнт звертається до 18 із них; окремий GET /api/products/{id} не використовується, оскільки товар береться зі списку. Це саме по собі не дефект. Покриття маршрутів не означає готовність усіх сценаріїв.

| Ділянка | Стан | Розрив |
| --- | --- | --- |
| Авторизація | login → Bearer → me відповідають серверу | Не враховано accessTokenExpiresAt, немає централізованої реакції на завершення сесії |
| Замовлення | Маршрути, create/item/status payload та основні поля відповідей збігаються | Заміна рядка через DELETE + POST неатомарна; коментар існуючого замовлення не зберігається |
| Переходи статусів | register/grant/ship/invoice/cancel та дозволені переходи збігаються | Правила дублюються в клієнті; isStatusFinal із API не використовується |
| Товари й залишки | Основні DTO та CRUD/stock-запити відповідають серверу | У реальному режимі помилка може підміняти товари демонстраційними записами |
| Звіти | Усі 5 маршрутів і основні поля реалізовані | Сервер повертає 500; завантаження допускає частковий стан; PDF може експортувати застарілі дані |
| Час формування звіту | Контракт розійшовся | Опублікована схема і ReportDtos.cs: generatedAt; окремий DTO і HTTP-клієнт: createdAt. Зараз клієнт використовує тільки text |
| Клієнти замовлень | Немає customers API | Список починається з LocalCatalog, доповнюється замовленнями; демонстраційне ім’я має перевагу за однакового ID |
| Користувачі, ролі, Telegram-доступ | Немає users API | Екран редагує TestUsers у пам’яті; зміни не потрапляють у БД |
| Права доступу | Частково лише у WPF | На Orders/Products/Reports немає Authorize; глобальної обов’язкової політики не задано. Director не може редагувати товари у WPF, хоча ТЗ це дозволяє; Manager не має розділу Products, хоча ТЗ дозволяє перегляд |

Клієнт також відкидає частину доступних полів: контактні дані покупця, currencyCode, updatedAt, createdByUserId, isStatusFinal. Це не ламає десеріалізацію, але звужує можливості UI; грошові підписи зараз фактично прив’язані до гривні.

## План за пріоритетами

### P0. Відновити збірку та працездатність звітів

1. **Залишити єдине визначення кожного DTO звітності.** Прибрати дублювання між ReportDtos.cs та шістьма окремими файлами. Узгодити час формування як generatedAt із поточною опублікованою схемою, оновити сервер і клієнт разом.
   - Готовність: повна solution збирається без CS0101/CS8863; контракт має одну назву поля часу.
2. **Переписати запити ReportsController так, щоб вони переводилися в SQL.** Фільтрувати й сортувати сутності/анонімні проєкції до фінального конструювання positional record DTO; агрегати виконувати на сервері БД. Перевірити саме з робочим EF-провайдером. Не переносити без обмежень усі таблиці в пам’ять.
   - Готовність: усі п’ять звітів повертають 200 для порожнього результату, однієї дати й діапазону; перевірити після розгортання.
3. **Заборонити експорт невдалого завантаження.** LoadReportsAsync має повертати результат або передавати помилку виклику експорту. Оновлювати набір звітів узгоджено; зберігати період, для якого реально отримані дані. Додати окремий стан завантаження звітів і блокування повторного запуску.
   - Готовність: збій будь-якого потрібного запиту не створює PDF зі старими цифрами під новим періодом; некоректний діапазон також зупиняє експорт.

### P0. Забезпечити права на сервері

4. **Додати авторизацію й політики ролей до бізнес-операцій.** Відтворити матрицю ТЗ для читання, редагування, статусів і звітності. Прибрати fallback currentUserId = 1: ідентичність має надходити з валідованого токена. Приховати детальні серверні exception-відповіді у розгорнутому середовищі.
   - Готовність: анонімні бізнес-запити повертають 401; заборонені ролі — 403; автор змін у журналі відповідає токену. Перевіряти записи в тестовому середовищі.
5. **Узгодити WPF із матрицею прав.** Дозволити Director керувати товарами, Manager переглядати їх; завантажувати звіти лише ролям із відповідним правом. Зараз LoadClientDataAsync викликає LoadReportsAsync для всіх ролей.
   - Готовність: навігація, команди і сервер однаково трактують кожну роль.

### P1. Завершити інтеграцію довідників

6. **Додати customers API та підключити його у WPF.** Мінімум — список і деталі; створення/редагування відповідно до погодженого сценарію. Прибрати LocalCatalog із реального режиму. До появи API показувати лише підтверджених покупців із реальних замовлень як тимчасове обмеження, без демонстраційних ID.
   - Готовність: доступний реальний покупець без попередніх замовлень; ім’я й ID у виборі відповідають БД.
7. **Додати users API для наявного екрана.** Список/читання, створення, редагування, активність, роль, Telegram-дозвіл і Telegram ID. Director — читання; Admin — керування. Пароль змінювати окремою операцією без повернення пароля або хешу клієнту.
   - Готовність: зміни переживають перезапуск, впливають на серверну авторизацію; екран більше не редагує TestUsers у реальному режимі. До інтеграції позначити або вимкнути недіючі операції.
8. **Прибрати автоматичну підміну товарів mock-даними.** Ізолювати LocalCatalog у явно вибраному mock-режимі. При збої реального API можна залишити попередні дані з позначкою застарілості, блокуючи небезпечні зміни; помилку конфігурації не трактувати як увімкнення demo.
   - Готовність: 404, таймаут або пошкоджений appsettings не призводять до надсилання демонстраційних productId на реальний сервер.

### P1. Зробити редагування замовлень надійним

9. **Додати атомарне оновлення рядка або всього замовлення.** Поточний ReplaceOrderItemAsync спочатку видаляє рядок, потім додає: збій другого запиту втрачає рядок, а нова ціна може відрізнятися від історичної. Сервер має зберігати зміни транзакційно, перевіряти статус і конкурентні зміни; правила зміни ціни визначити явно.
   - Готовність: невдала зміна кількості не змінює початкове замовлення; повторна спроба не створює дублікати; фінальні замовлення захищені на сервері.
10. **Узгодити поля редактора з доступними операціями.** Коментар доступний для введення і при редагуванні, але SaveEditedOrderItemsAsync його не надсилає. Додати серверне оновлення коментаря або зробити його лише для читання в цьому режимі. Валідувати відсутніх/неактивних покупців і товари, дублікати та недопустимі кількості; очікувані помилки повертати як 400/404/409.
   - Готовність: кожне доступне для редагування поле справді зберігається або UI явно обмежує дію.

### P2. Узгодити контракти, час і завантаження

11. **Уніфікувати API-помилки та сесію.** Єдиний формат ProblemDetails/ValidationProblemDetails, парсер message/title/detail/errors для всіх запитів, збереження HTTP-коду; контроль accessTokenExpiresAt і зрозумілий повторний вхід на 401. Refresh-token flow додавати лише разом із серверною підтримкою.
12. **Доповнити OpenAPI типами відповідей і помилками.** Частина actions повертає IActionResult без типізованої response-схеми; цього недостатньо для повноцінного генерованого клієнта. Далі обрати спільну бібліотеку DTO або генерацію клієнта зі схеми, щоб уникнути ручних розходжень.
13. **Визначити часову зону й зміст звітів.** Зараз UI використовує DateTime.Today, API трактує дату як UTC через SpecifyKind, а час формування бере через DateTime.Now. Узгодити календарний день у Europe/Kyiv та його UTC-межі. Окремо визначити, чи скасовані/незавершені замовлення входять у «продажі»: зараз агрегація включає всі статуси. Валідувати from <= to і на сервері.
14. **Прибрати повне завантаження деталей усіх замовлень при кожному оновленні.** Зараз іде послідовний GET для кожного замовлення, далі ще п’ять звітів. Завантажувати деталі за вибором, агрегати брати зі звітів; розділити стан Dashboard і звітного періоду. Додати пагінацію/серверні фільтри, коли обсяг потребуватиме.
15. **Завершити використання даних та локалізацію.** За потребою UI передавати валюту, контакти покупця, фінальність статусу і час оновлення. Локалізувати текст періоду, підсумків і PDF; manager-summary зараз формується сервером українською незалежно від мови клієнта.

## Порядок виконання та перевірка

1. Окреме виправлення DTO + LINQ звітів; повна збірка й перевірка п’яти звітів на реальному EF-провайдері.
2. Виправлення стану звітів/PDF та обробки помилок у WPF.
3. Серверні політики ролей + синхронне оновлення WPF; перевірка матриці 401/403/дозволені дії.
4. Customers API, потім users API та видалення mock-підмін із реального режиму.
5. Транзакційне редагування замовлень, збереження коментаря, перевірки бізнес-правил.
6. Контрактні перевірки, часова зона, оптимізація завантаження та локалізація.

Обов’язкові сценарії приймання: вхід/завершення сесії; створення замовлення з реальним покупцем; успішна й невдала зміна рядка; переходи й фінальність статусів; права кожної ролі; звіти за порожній/непорожній період; межа календарного дня; помилка завантаження перед PDF; збереження користувачів після перезапуску.

Нові endpoints у цьому плані є пропозиціями для backend. У поточній опублікованій схемі customers/users та атомарного оновлення замовлення немає.
