# Технічне завдання

## Проєкт

**Назва:** Система опрацювання замовлень Orders  
**Тип:** WebAPI application на C# + тонкий десктопний клієнт WPF C# + Telegram-бот  
**Методологія управління:** Agile Scrum  
**Тривалість планування:** початкові 3 спринти та 3 додаткові спринти розширення

**Редакція вимог:** 25.10.2026; описує цільову функціональність, а не підтвердження її реалізації.

## 1. Мета проєкту

Розробити програмну систему для опрацювання замовлень на товари, які зберігаються у базі даних на віддаленому сервері.

Система має забезпечити:

- створення та ведення замовлень;
- адміністрування каталогу товарів;
- контроль переходів замовлення між дозволеними станами;
- заборону дій, які суперечать бізнес-правилам;
- розмежування доступу користувачів за ролями;
- доступ до функціональності через WebAPI;
- роботу тонкого десктопного клієнта на WPF;
- збір інформації та статистики через Telegram-бота;
- формування і відправлення керівнику звіту через Telegram за окремим запитом.

## 2. Команда та Scrum-ролі

У проєкті беруть участь 3 учасники. Через малий склад команди Scrum-ролі та технічні обов'язки можуть суміщатися одними й тими самими учасниками.

### Product Owner

Відповідає за вимоги, пріоритети Product Backlog, приймання результатів спринтів і уточнення бізнес-правил. У межах навчального проєкту роль може виконувати один з учасників команди.

### Scrum Master

Організовує Scrum-процес, стежить за проведенням планувань, daily sync, review та retrospective, допомагає усувати блокери. У межах команди з 3 учасників роль може суміщатися з технічною роллю.

### Development Team

Відповідає за проєктування, розробку, тестування та інтеграцію системи.

### Розподіл відповідальності між 3 учасниками

| Учасник | Основна зона відповідальності | Додаткові обов'язки |
| --- | --- | --- |
| Учасник 1 | Backend WebAPI, доменна модель, правила станів замовлення | Product Owner, уточнення вимог, приймання результатів спринту |
| Учасник 2 | WPF-клієнт, взаємодія з WebAPI, робота з БД, клієнтська валідація | Scrum Master, організація Scrum-процесу, контроль дошки Trello |
| Учасник 3 | Telegram-бот, статистика, звіти та тестування | QA, перевірка інтеграцій, підготовка документації |

Команда працює спільно над плануванням спринтів, оцінкою задач, review результатів і фінальним тестуванням. Для задач із високим ризиком допускається парна робота або взаємна перевірка між учасниками.

### Принцип паралельної розробки

Розробка у спринтах має виконуватися паралельно за напрямами, щоб кожен учасник мав власний потік роботи та команда не чекала повного завершення одного модуля перед початком іншого.

Основний підхід:

- Учасник 1 працює над backend API, доменною логікою та правилами доступу.
- Учасник 2 паралельно працює над WPF-клієнтом і БД, використовуючи погоджені DTO, mock-дані або тестові endpoints.
- Учасник 3 паралельно працює над Telegram-ботом, тестуванням, seed-даними та документацією.
- Інтеграція результатів виконується наприкінці кожного спринту або після завершення ключової задачі.
- Якщо API ще не готове, WPF-клієнт може тимчасово використовувати mock-сервіси, але після появи endpoints має бути переключений на реальний backend.
- На Sprint Review демонструється не лише окремий модуль, а узгоджений інкремент системи.

## 3. Зацікавлені сторони

- Керівник, який отримує статистику та звіти;
- Оператор або менеджер, який створює та опрацьовує замовлення;

## 4. Межі системи

### Входить у проєкт

- C# ASP.NET Core WebAPI, тонкий WPF-клієнт і Telegram-бот;
- замовлення, покупці, каталог товарів, ціни й залишки;
- автентифікація та серверна перевірка актуальних прав;
- створення, блокування/розблокування й видалення ролей тільки Admin;
- налаштування видимості розділів для ролей тільки Admin;
- один динамічний workflow, серверна state machine, API конфігурації та редактор WPF тільки для Admin і Director;
- перетягування замовлень між колонками з перевіркою переходів і версій;

- PostgreSQL з доступом через предметні інтерфейси;
- логування, зрозумілі помилки, тестування ключових правил і конкурентних змін.

### Поза поточним обсягом

- довільні скрипти правил, повноцінний BPMN/Jira та кілька незалежних workflow;
- дизайнер сторінок звітів, довільні SQL/HTML/формули й складна BI;
- права на рівні окремих полів/записів та універсальний редактор прав усіх дій;
- повний складський облік із резервуванням, багаторівнева CRM і мобільний клієнт.

## 6. Ролі користувачів і права доступу

### Системні ролі та фіксовані можливості

| Роль | Права |
| --- | --- |
| Admin | Керування користувачами, ролями та видимістю; редактор workflow; товари, замовлення, статистика, звіти |
| Director | Редактор workflow; керування товарами й замовленнями; перегляд користувачів, статистики й звітів; без керування користувачами, ролями та видимістю |
| Manager / Operator | Створення й опрацювання замовлень, перегляд товарів, дозволені переходи |
| Viewer | Перегляд дозволених розділів без зміни даних |
| Створена Admin роль | Початково без дозволів; перегляд налаштовує Admin, переходи — редактор workflow; без автоматичних привілеїв системних ролей |

TelegramBot — додаткова захищена системна службова роль без доступу до звичайних екранів; її обмеження задає контракт інтеграції бота.

Початкова видимість відтворює наявну рольову модель. Дозвіл бачити розділ не надає права змінювати дані. Інші права дій системних ролей зберігаються. Власній ролі можна призначити дозволений перехід, але це не надає створення/редагування замовлень чи товарів автоматично.

`Workflow.Manage` фіксований тільки за системними Admin і Director. `Roles.Manage`, `Roles.ManageVisibility` і керування користувачами — тільки за Admin; ці привілеї не видаються через матрицю видимості або збіг назви ролі.

### Керування ролями — тільки Admin

- Створення ролі з унікальним незмінним кодом, назвою, ознаками isActive/isSystem, версією та часовими позначками. Код системної ролі зарезервований, isSystem не приймається як кероване клієнтом поле.
- Редагування назви, блокування й розблокування виконуються з перевіркою очікуваної версії.
- Заблоковану роль не можна призначити новому користувачу. Її користувачі не можуть увійти чи виконувати захищені запити, зокрема зі старим JWT або через Telegram. Права й активність користувача та ролі перевіряються за актуальними даними сервера на кожен запит.
- Блокування не видаляє користувачів, призначення, переходи чи історію. Після розблокування можливий новий вхід; JWT, термін якого ще не закінчився, знову проходить перевірку активності. Примусове відкликання токенів — окрема майбутня функція.
- Admin заборонено блокувати чи видаляти як роль; не можна видалити, деактивувати або перепризначити останнього активного адміністратора. Перевірка атомарна.
- Інші системні ролі можна блокувати, але не видаляти. Користувацьку роль можна видалити тільки без посилань від користувачів (навіть неактивних), Telegram-прив'язок, опублікованих переходів, збереженої чернетки або інших записів. Інакше — 409 із залежностями; каскадне видалення заборонено.
- Адміністративні API ролей недоступні Director. Мінімальні довідники ролей для редактора переходів видаються через його дозволені endpoints.

### Видимість розділів — тільки Admin

Налаштовується перегляд огляду, замовлень, дошки, товарів, покупців, користувачів, звітів, доставки та платежів. Каталог дозволів фіксований у коді; призначення зберігаються в role_permissions. Невідомий або відсутній дозвіл означає відмову. Для дошки потрібні Board.View та Orders.View.

WPF будує навігацію за ефективними можливостями API. Сервер захищає ті самі дані, включно з вкладеними DTO, PDF і Telegram; приховані дані не можна отримати іншим маршрутом. Після 403 або оновлення можливостей клієнт закриває недоступний розділ і очищає його дані. Матриця й рольові записи захищені версіями від одночасного перезаписування.

## 7. Стани замовлення

Стани замовлень зберігаються в БД й налаштовуються тільки Admin і Director через API та редактор WPF. Один спільний опублікований workflow застосовується до всіх замовлень; чернетка не впливає на роботу до публікації.

Початковий шаблон містить NewOrder, Registered, Granted, Shipped, Invoiced, Cancelled. Invoiced означає «виставлено рахунок» і сам по собі не підтверджує оплату. Оплата зберігається окремо; за потреби додається Paid із перевіркою PaymentSucceeded. Кожен стан має назву, незмінний код, порядок, активність, початковість, фінальність, категорію, дозвіл редагувати позиції та колір.

Колонки дошки, фільтри, доступні дії та розподіл статистики завантажуються з API. Довільний новий стан з'являється без перекомпіляції клієнта. Назва стану не є доказом фінансової події.

## 8. Правила переходів між станами

Початкові переходи шаблону:

| Звідки | Куди | Дія |
| --- | --- | --- |
| NewOrder | Registered | Реєстрація |
| NewOrder | Cancelled | Скасування |
| Registered | Granted | Погодження |
| Registered | Cancelled | Скасування |
| Granted | Shipped | Відправлення |
| Granted | Cancelled | Скасування |
| Shipped | Invoiced | Виставлення рахунку |

Для кожного переходу задаються назва дії, дозволені ролі й правила з каталогу: HasItems, ProductsActive, StockAvailable, CustomerPhoneRequired, CommentRequired; після інтеграцій — PaymentSucceeded та ShipmentCreated. Умови об'єднуються AND; довільні скрипти не підтримуються. Новий тип правила додається серверним кодом, налаштування відомого типу — через редактор.

Серверна state machine в одній транзакції перевіряє актуального користувача/роль, версії замовлення і workflow, поточний стан, дозволений перехід та правила; зберігає новий стан та один запис історії. Усі маршрути зміни стану використовують цей сервіс. Пряме довільне присвоєння statusId через API заборонене.

Публікація має перевіряти рівно один початковий стан, унікальні коди, посилання, досяжність, тупики й відсутність виходів із фінальних станів. Вона показує вплив на поточні замовлення та атомарно підвищує revision. Використані стани/коди не видаляються; деактивація зайнятого стану чи втрата виходу потребує попереднього перенесення замовлень. Публікація й переходи узгоджено захищають revision від гонок.

Відхилений перехід не змінює дані. Конфлікт версії повертає 409; клієнт перечитує актуальні дані й не виконує наступний перехід автоматично.

## 9. Бізнес-правила

- Позиції редагуються тільки за canEditItems поточного нефінального стану та відповідного права користувача. У початковому шаблоні це NewOrder і Registered.
- Додавати можна лише активні товари з додатною ціною й кількістю в межах доступного залишку. Створення та редагування використовують узгоджені перевірки.
- Ціна існуючої позиції зберігається як історичний знімок; зміна каталогу її не переписує.
- Реєстрація потребує позицій; погодження перевіряє доступність товарів і кількості. Інваріанти цілісності, прав і фінальності не можна вимкнути через редактор правил.
- Перевірка залишку не є резервуванням; повний облік резервів не входить у цей етап.
- Кожний успішний перехід створює один запис історії. Заблокована роль не може виконувати переходи навіть за наявності старого дозволу.
- Платіж, доставка й бізнес-стан замовлення обліковуються окремо. Накладна не доводить фізичного відправлення; Invoiced не доводить оплати.
- Після створення активної оплати склад і суму замовлення змінювати заборонено. Пізній успіх після скасування фіксується й потребує ручної обробки.
- Помилки містять зрозумілу причину; операція або завершується повністю, або не залишає часткових змін.

## 10. Функціональні вимоги

### Автентифікація та сесія клієнта

POST /api/auth/login приймає {login, password}, POST /api/auth/refresh — {refreshToken}. Обидва endpoints повертають однаковий JSON із двома токенами та окремим часом спливання кожного:

```json
{
  "accessToken": "<access-token>",
  "accessTokenExpiresAt": "2026-10-25T10:15:00Z",
  "refreshToken": "<refresh-token>",
  "refreshTokenExpiresAt": "2026-11-08T10:00:00Z",
  "tokenType": "Bearer"
}
```

Поля — camelCase; дати — UTC ISO 8601 із часовою зоною. Приклади дат ілюстративні. Обидві дати обов'язкові; клієнт використовує серверний час спливання, а не фіксований TTL у своєму коді. Успішний refresh ротує refresh token і повертає нову пару та строки її дії. Сервер зберігає лише хеш refresh token, строк дії й стан сесії. Профіль користувача отримується через /api/auth/me.

WPF-клієнт повинен підтримувати цей контракт у DTO, IAuthApiClient, HttpOrdersApiClient і моделі сесії:

- Обидва токени та їх дати зберігаються в пам'яті; пароль після login не зберігається. Access передається як Bearer у бізнес-запитах, refresh — тільки в /api/auth/refresh.
- Клієнт завчасно оновлює access, наприклад за 30 секунд до спливання. Паралельні запити очікують одну спільну операцію refresh; нова пара й дати замінюються атомарно.
- Спливання access не завершує сесію, якщо refresh дійсний. Після 401 дозволяється один refresh та один повтор запиту, відхиленого API до виконання. Відповідь 403 не запускає refresh; операції запису після невідомого результату/timeout не повторюються автоматично.
- Прострочений, відкликаний або відхилений refresh завершує сесію: обидва токени, дати й дані користувача очищаються, відкривається вхід. При мережевій помилці немає циклу повторів; після невідомого результату ротації старий refresh автоматично не надсилається знову.
- Вихід скасовує запити й очищає сесію. Пізня відповідь refresh не може відновити користувача після виходу чи зміни сесії. Профіль і дозволи оновлюються так, щоб роль у WPF не залишалася застарілою.
- Секрети не логуються та не записуються у звичайні файли/налаштування. Python-клієнт бота читає той самий формат токенів і дат із правилами службової сесії BOT_INTEGRATION.md.

### WebAPI

Зберегти CRUD замовлень, позицій, товарів, покупців, користувачів, автентифікацію та JSON-статистику. Бізнес-правила виконуються сервером; WPF і Telegram працюють лише через API.

| Напрям | Орієнтовні endpoints |
| --- | --- |
| Ролі — тільки Admin | GET/POST /api/roles; PUT /api/roles/{id}; PUT /api/roles/{id}/active; DELETE /api/roles/{id} |
| Дозволи | GET /api/permissions; GET /api/roles/permissions; PUT /api/roles/{roleId}/permissions — Admin; GET /api/auth/me/permissions — поточний користувач |
| Workflow | GET /api/workflow; GET /api/workflow/rule-types; GET/PUT /api/workflow/draft; POST /api/workflow/draft/validate; POST /api/workflow/draft/publish |
| Переходи | GET /api/orders/{id}/transitions; POST /api/orders/{id}/transitions/{transitionId} |
| Звіти | CRUD /api/report-templates; POST /api/reports/pdf |
| Доставка | GET /api/delivery/cities; GET /api/delivery/warehouses; GET/POST /api/orders/{id}/shipment; POST /api/orders/{id}/shipment/refresh |
| Оплата | POST/GET /api/orders/{id}/payments; POST /api/payments/{id}/refresh; POST /api/payments/liqpay/callback |

Робочий workflow доступний користувачам із правом перегляду замовлень та редакторам. Чернетка, каталог правил, перевірка й публікація — тільки Admin/Director. Чернетка зберігається одним PUT із expectedDraftVersion; публікація перевіряє також expectedWorkflowRevision. Переходи приймають expectedVersion замовлення, revision workflow і коментар. Зміни ролі приймають expectedVersion; DELETE перевіряє If-Match. Довідники ролей для редактора переходів не відкривають адміністративне API ролей Director.

API повертає DTO; неавтентифікований запит — 401, відсутність прав — 403, відсутній об'єкт — 404, конфлікт версії/залежностей — 409, невалідні дані/правила — узгоджений 400 або 422.

### WPF

- Зберегти вхід, списки, деталі та форми замовлень/товарів/покупців/користувачів відповідно до прав.
- «Ролі й доступ» тільки для Admin: створення, назва, блокування/розблокування, видалення з причинами обмежень, матриця видимості. Системні й заблоковані ролі позначаються явно.
- «Налаштування workflow» тільки для Admin/Director: списки/форми станів і переходів, ролі, правила, збереження чернетки, перевірка, публікація. Конфлікт не перезаписує чужі зміни; незбережені зміни не губляться мовчки.
- Drag-and-drop починається після порогу руху миші; дозволені колонки підсвічуються. Drop у поточну колонку — no-op, поза дошкою — скасування. Порожня колонка є ціллю. Для кількох переходів у той самий стан потрібен вибір; для обов'язкового коментаря — діалог.
- Виконується один запит на перенесення; повтор для картки блокується, переміщення завершується після успіху API. Версія відповідає даним, які користувач бачив до drag. На timeout перечитати стан/історію; на 409 оновити картку. Оновлюються суми, лічильники й фільтри. Зміна стану кнопкою зберігається; ручне сортування карток не входить у цей етап.

### Звіти

Прості шаблони: тип даних (замовлення, продажі, залишки, зведення), заголовок, колонки й їх порядок, фільтри, сортування, одна група, підсумки, примітка, орієнтація. Редактор використовує відомі поля й блоки; SQL/скрипти/довільний HTML не приймаються.

Спільні шаблони редагують Admin/Director, формують PDF користувачі з Reports.View та потрібними правами джерела/блоків. Сервер перевіряє JSON-схему, версію, поля, права й обсяг, формує PDF через QuestPDF із включеними українськими шрифтами. Відповідь application/pdf; клієнти отримують готові байти, попередній перегляд також формується сервером. JSON-звіти залишаються для екранів.

Визначити бізнес-критерій продажу; для фінансових підсумків використовувати підтверджені платежі, тестові позначати окремо. Межі дат Europe/Kyiv переводяться в UTC з урахуванням літнього часу. Формування синхронне з лімітами рядків, періоду й часу.

### Тестові інтеграції

Нова Пошта / Nova Post: спочатку з тестовим ключем перевірити доступність потрібного маршруту, довідників, створення й відстеження. API 2.0 і Nova Post мають різні контракти/ключі. Мінімум — вибір міста/відділення, одержувач, вага/місця/вартість, налаштований відправник, одна активна доставка, створення й ручне оновлення статусу. Якщо sandbox-сценарій недоступний, демо на fake позначається як емуляція й не вважається підтвердженою зовнішньою інтеграцією.

LiqPay sandbox: сервер визначає суму/валюту й створює унікальну спробу; клієнт відкриває Checkout у браузері, картка вводиться лише у провайдера. Callback на публічний HTTPS перевіряє підпис, мерчанта, ids, суму, валюту й Test-режим. Повторна обробка ідемпотентна, старий Pending не перезаписує успіх. Повернення браузера не підтверджує оплату; пропущений callback перевіряється status API. Алгоритм підпису звірити з обраною версією контракту та реальним sandbox callback.

Обидві інтеграції мають адаптер і fake для перевірок. Зовнішні виклики виконуються поза транзакціями БД; невідомий результат не запускає сліпого повторного створення. Секрети лише на сервері. Callback фіксує платіж, а бізнес-перехід у першій версії виконує користувач через workflow.

### Telegram

Обов'язковий контракт — BOT_INTEGRATION.md у Documentation поза репозиторієм. Описані ним можливості є вимогами до реалізації, а не підтвердженням наявних API.

- Бот працює через HTTPS як службовий користувач telegram-bot із захищеною системною роллю TelegramBot. Вона дозволяє лише /api/bot/...; login і refresh використовують /api/auth/login та /api/auth/refresh. Роль не надає людських адміністративних прав і не отримує їх через матрицю видимості.
- Access token діє 15 хвилин, refresh — 14 днів із ротацією та відкликанням сесії при повторному використанні. Сервер перевіряє актуальні користувача, роль і зміну облікових даних; БД містить хеші refresh/link tokens. Бот тримає токени лише в пам'яті й виконує один refresh за раз.
- GET /api/bot/users/{id} повертає актуальну прив'язку й дозволи для кожного повідомлення. POST /api/bot/users/{id}/link одноразово обмінює payload /start на прив'язку; DELETE /api/bot/users/{id}/link відв'язує; POST /api/bot/users/{id}/report формує звіт. Генерація короткоживучого link token і адміністративне відв'язування мають окремі дозволені desktop API.
- Bot API повертає JSON camelCase, дозволи orders.read, reports.read, reports.telegram.send, telegram.link; один каталог прав узгоджує їх із WPF. Помилки — application/problem+json з code згідно з контрактом: not_linked, link_invalid, telegram_already_linked, bind_failed, forbidden, network_denied.
- /start, /help, /me, /report, /unlink — обов'язкові команди. /stats і /orders_today залишаються розширенням лише після появи окремих bot endpoints та дозволів; службовий токен не обходить заборону звичайних API.
- /report підтримує JSON {type: text, text: ...} та готові файлові байти з Content-Disposition. Після реалізації серверного PDF /report надсилає цей файл. Локальне формування звіту чи fallback на бізнес-дані іншого користувача заборонені.
- API є єдиним джерелом користувачів, прив'язок і прав; бот не зберігає їх у локальному SQLite/файлах і не кешує довше кількох секунд. API не звертається до Telegram і не отримує Telegram bot token.
- Обробляються лише приватні текстові повідомлення реальних користувачів; Telegram id береться з from.id. Неприв'язаним користувачам бот мовчить, крім пояснення /start. Повідомлення — plain text, за потреби розбиті до ліміту Telegram. Секрети й /start payload не логуються.
- TLS перевіряється, redirect із токеном заборонений. Link не повторюється автоматично після timeout; повтори безпечних викликів обмежені. Login обмежений 5/хв на IP, redeem — 10/хв на Telegram id; підтримується налаштований allowlist IP. Для webhook потрібні secret header і deduplication; рекомендований long polling.
- Блокування користувача/ролі застосовується до наступного bot API запиту незалежно від старого JWT або Telegram-прив'язки. Права повторно перевіряються при кожному виклику.

## 11. Нефункціональні вимоги

- ASP.NET Core WebAPI і WPF на C#, Telegram-бот на Python; прості сервіси та невеликі view model.
- Клієнти не містять правил доступу як єдиного захисту й не підключаються прямо до БД.
- Сервер перевіряє актуальні права, активність користувача/ролі, версії та бізнес-правила; відсутній користувач не підміняється Admin/id=1.
- Міграції зберігають існуючі дані; для кожної СУБД перевіряються точність сум, дати, атомарність і конкурентні записи.
- Генерація PDF перевіряється на цільовому хостингу; українські шрифти постачаються із сервером.
- Ключі, токени й connection strings зберігаються в секретах/оточенні, не в репозиторії чи клієнтських DTO.
- Помилки зрозумілі й мають коректні HTTP-статуси; критичні помилки логуються без секретів.
- Ключові правила, права, повтори інтеграцій та конкуренція перевіряються автоматично; дошка й PDF також вручну/візуально.

## 12. Архітектура

Зберегти поточні проєкти WebApi, Application, Domain, Infrastructure, WpfClient, TelegramBot і тести.

Потік: Controller → Application service → предметні repository/query-інтерфейси та інтерфейс транзакцій → Infrastructure → БД.

Усі операції з БД, зокрема ролі, дозволи, workflow, звіти, доставки й платежі, проходять через інтерфейси Application. Перевикористати IOrderRepository, IProductRepository, IUserRepository, IUnitOfWork; доповнити потрібними операціями й невеликими інтерфейсами. Контролери не використовують AppDbContext/Npgsql; бізнес-сервіси не отримують DbSet/IQueryable/SQL. Блокування й специфічні помилки приховані в реалізаціях; репозиторії однієї транзакції використовують спільну сесію.

Database:Provider та рядок підключення вибирають реалізацію при запуску API; перемикання потребує перезапуску, не переносить дані та не змінює бізнес-код/API клієнтів. Підтримувана СУБД — PostgreSQL. Доступ до неї ізольований інтерфейсами Application.

Один OrderWorkflowService, невеликий каталог перевірок, один сервіс PDF та адаптери зовнішніх провайдерів. WPF-редактори ролей, workflow і звітів мають окремі view model. Мікросервіси, брокер і універсальний workflow-двигун для цього обсягу не потрібні.

## 20. Критерії приймання системи та розширення

- Базові замовлення, покупці, товари, історичні ціни й історія працюють через API відповідно до прав.
- Admin створює роль, налаштовує видимість, призначає її користувачу, блокує/розблоковує; Director/Manager/Viewer не можуть виконати ці дії прямим API-запитом.
- Блокування забороняє новий вхід і захищені запити зі старим JWT та через Telegram. Заблокована роль недоступна для нових призначень.
- Роль із залежностями не видаляється; повертається 409 без втрати даних. Системні ролі не видаляються, Admin не блокується, останній активний адміністратор захищений.
- Заборона перегляду прибирає розділ у WPF і блокує його дані в API, PDF, вкладених DTO та Telegram; перегляд не надає права редагування.
- Admin і Director у WPF додають стан, перехід, дозволену роль і правило, зберігають чернетку, перевіряють та публікують. Інші ролі не мають доступу. Невалідна чернетка не впливає на роботу.
- Новий стан з'являється в дошці/фільтрах/статистиці без перекомпіляції. Заборонені переходи не виконуються, фінальні стани захищені.
- Одночасні перенесення картки створюють один перехід та один запис історії; конфлікт, timeout і повтор не залишають хибного стану в UI.
- Користувач із потрібними правами формує PDF за шаблоном; WPF/Telegram отримують готовий файл. Українські шрифти, багатосторінкові таблиці, дати й підсумки коректні на сервері.
- Тестова доставка не дублюється при повторі; невідомий результат можна звірити. Емуляція явно позначена і не видається за sandbox провайдера.
- LiqPay sandbox проходить успіх, відмову, повтор/невалідний callback і звірку пропущеного повідомлення. Сума/валюта перевіряються, тестові платежі позначені, Invoiced не дорівнює підтвердженій оплаті.
- Усі поточні операції PostgreSQL ізольовані інтерфейсами, зокрема початкове встановлення паролів. Чинні API/DTO працюють; транзакції, конфлікти, суми й дати перевірені на PostgreSQL.
- Login і refresh повертають обидва токени та обидві дати спливання. WPF оновлює access без повторного введення пароля, виконує один refresh при паралельних запитах, використовує ротований refresh і завершує сесію після його спливання/відкликання. Пізній refresh не відновлює сесію після виходу.
- Bot API проходить link/replay/unlink, refresh rotation, перевірки актуальних прав і деактивації з BOT_INTEGRATION.md; токени не зберігаються відкрито чи на диску бота.
- Solution збирається; відповідні автоматичні та ручні перевірки пройдені; DTO/API, інструкції й усі копії ТЗ узгоджені.
